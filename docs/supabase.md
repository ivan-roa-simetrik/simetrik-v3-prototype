# Supabase (persistencia)

> Última actualización: 2026-08-18
> Este archivo es distinto a los demás de `docs/`: no documenta una pantalla, documenta la **capa de persistencia** del prototipo — hasta el 2026-08-14 el prototipo no tenía ninguna (todo vivía en arrays JS en memoria o directo en el DOM, se perdía en cada reload). Ver `proyecto.md`/`apps.md`/`project-map.md` para los modelos conceptuales que este archivo traduce a esquema real.

## Propósito

Persistir en una base de datos real (Supabase/Postgres) lo que hoy vive hardcodeado en `flows/home/index.html` (`PROJECTS_DATA`, `APPS_DATA`, `CHATS_DATA`, `PANEL_AGENTS_DATA`) y reemplazar el login falso (`setTimeout` + redirect) por autenticación real, sin romper la naturaleza del prototipo (HTML estático, sin build step). El plan completo está en 6 fases; este documento cubre **Fase 0** (fundaciones: esquema + auth), **Fase 1** (lectura real), **Fase 2** (escritura real), **Fase 3** (mensajes de chat reales) y **Fase 4** (Realtime: sincronización en vivo entre sesiones). Fases 5-6 (mapa del proyecto, RLS fino por rol) siguen pendientes — ver "Pendiente/abierto".

## Decisiones tomadas

- **2026-08-14 — Proyecto Supabase nuevo y separado** del que ya usa el prototipo hermano `mock-v3` (no compartir). Motivo: v3.1 tiene su propio ciclo de decisiones y no debe acoplarse a ni arriesgar el otro prototipo. `mock-v3` sirvió como **precedente de patrón** (mismo stack: HTML/JS estático + supabase-js vía CDN, sin build step), no como base de datos compartida.
- **2026-08-14 — Multi-organización desde el día 1**, no single-tenant primero. Motivo: agregar `organization_id` retroactivamente después de tener datos reales obliga a re-migrar todo y reescribir RLS — mismo patrón (`organizations`/`organization_members` con enum de roles) ya validado en `mock-v3/supabase/migrations/0001_organizations.sql`. Roles disponibles desde ya (`org_admin`/`builder`/`operator`/`auditor`) pero **sin uso real todavía** — cualquier miembro de la organización puede ver/crear/editar/borrar dentro de ella (ver `proyecto.md` para el modelo de roles/permisos por proyecto que falta traducir a RLS fino).
- **2026-08-14 — Un chat pertenece a lo sumo a UN contexto** (project, app o agent) o a ninguno — nunca a varios a la vez. Confirma el shape `{ type, id }` que `CHATS_DATA` ya usaba en memoria. Modelado como 3 FKs nullable + `CHECK` (a lo sumo una no-nula) en vez de un par polimórfico `context_type`/`context_id`, para no perder integridad referencial real ni los `on delete cascade`.
- **2026-08-14 — Sin tabla "map" intermedia**: los nodos/edges del Project Map cuelgan directo de `project_id` — mismo criterio que el repo real de Simetrik v3 (`backend/src/db/schema.ts`), que tampoco tiene una entidad "mapa" separada.
- **2026-08-14 — Versionado del mapa = snapshot completo por versión**, no un log de cambios liviano. Decisión explícita del usuario, adelantando a nivel de esquema lo que el plan del mapa (ver memoria de sesión "project-view-map-plan") tenía como backlog P3 ("full Audit mode"). Mismo contrato que `AUDIT_ROLLBACK_EXAMPLE` del mock: un rollback crea una versión **nueva** apuntando hacia atrás vía `source_version_id`, nunca borra ni reescribe historial.
- **2026-08-14 — Autoría por columna en la propia fila** (`created_by_user_id`, `origin_message_id`) en vez de una tabla de auditoría aparte para nodos/versiones — mismo patrón que la decisión D40 del repo real de Simetrik v3.
- **2026-08-18 — Setup vía dashboard + SQL Editor, no CLI.** El login interactivo de `supabase login` no funciona en este entorno (sin TTY para el flujo OAuth por navegador). En vez de generar un Personal Access Token y exponerlo en el chat, el usuario creó el proyecto manualmente desde `supabase.com/dashboard` y corrió las 4 migraciones a mano en el SQL Editor — cero tokens/passwords pasaron por la conversación. Costo: no hay `supabase/config.toml` ni link local al proyecto remoto (igual que `mock-v3`, que tampoco lo tiene) — futuras migraciones se siguen aplicando a mano en el SQL Editor, en orden, hasta que se decida invertir en CLI real.
- **2026-08-18 — Login real reemplaza el prellenado de demo.** El commit del 2026-08-12 había dejado el form de login con `email`/`password` prellenados (`ivan.roa@simetrik.com` / `demo1234`, ver `docs/README.md` historial) porque el submit era un `setTimeout` falso. Con auth real esos valores prellenados ya no tienen sentido (esa password no es la real de ningún usuario) — los campos volvieron a vacíos con placeholder.
- **2026-08-18 — Fase 1 mínimamente invasiva: mismos nombres de variable, mismo shape.** `PROJECTS_DATA`/`APPS_DATA`/`CHATS_DATA`/`PANEL_AGENTS_DATA` pasaron de `const [...]` (seed hardcodeado) a `let []` poblado por 4 funciones `load*FromSupabase()` que mapean filas snake_case de Postgres al mismo shape camelCase que `getFilteredProjects`/`applyAppsFilters`/`renderChatsList`/etc. ya consumían — cero cambios en el resto del código de filtrado/render. Carga fire-and-forget (`bootstrapDataFromSupabase`, un IIFE async) disparada apenas arranca el script, en paralelo para los 4 recursos.
- **2026-08-18 — `owner` de Project pasa de string plano a derivado de `owner_user_id`.** `'you'`/`'shared'` ya no es una etiqueta hardcodeada por proyecto — se calcula comparando `projects.owner_user_id` (columna real) contra el `user.id` de la sesión activa. Efecto secundario esperado: como el seed de `0002_projects_apps_agents.sql` no seteó `owner_user_id` en ningún proyecto, los 3 salen como `'shared'` ahora (antes 2 de los 3 mostraban `'you'` en el mock) — cosmético, no bloqueante; se puede corregir corriendo un `update projects set owner_user_id = '<tu-user-id>' where name in (...)` si se quiere restaurar exactamente la demo original.
- **2026-08-18 — `chat.createdAt` pasa de string decorativo a tiempo relativo real.** Antes era texto fijo por chat (`'2 days ago'`, nunca recalculado). Ahora `formatRelativeTime()` lo deriva del `created_at` real de la fila en cada carga — los chats sembrados en `0003_chats.sql` van a mostrar tiempos relativos a cuándo se corrió esa migración, no los valores originales del mock.
- **2026-08-18 — Sin selector de organización todavía, RLS scopea implícito.** Las 4 consultas (`select('*')` sin `.eq('organization_id', ...)`) confían en que RLS ya filtra por organización del usuario — correcto mientras el usuario pertenezca a una sola organización. Si se agrega una segunda organización antes de construir un selector en la UI, sus datos se mezclarían en las mismas 4 vistas sin ninguna distinción visual.
- **2026-08-18 — Flash de estado vacío aceptado, no resuelto.** `initProjectsView()`/`initAppsView()` renderizan de forma síncrona apenas carga la página (no solo al navegar ahí) — con los arrays arrancando vacíos, esto pinta brevemente "No projects match your search."/"No apps match your search." hasta que `bootstrapDataFromSupabase()` resuelve y fuerza un segundo render. Se evaluó reusar el skeleton ya existente (`showProjectsSkeleton`/`showAppsSkeleton`) pero el orden de ejecución síncrono del script haría que `initProjectsView()` lo pisara antes de que la promesa resolviera — requeriría reordenar cuándo se llama `initProjectsView()`/`initAppsView()`, fuera de alcance para esta pasada. Chats no tiene este problema (su primer render real ya es diferido a la navegación, no ocurre al cargar la página).
- **2026-08-18 — Fase 2: mutar en memoria primero, persistir después, sin rollback.** Cada función de escritura (crear/renombrar/pinear/archivar/borrar/editar) actualiza el array local y re-renderiza de inmediato (misma responsividad de siempre), y recién después dispara el `insert`/`update`/`delete` contra Supabase — si ese llamado falla, se loguea a consola (`console.error`) pero la UI no revierte el cambio optimista ni avisa al usuario. Suficiente para un prototipo; una app real necesitaría manejo de error visible + reintento o rollback.
- **2026-08-18 — Ids ahora los asigna Supabase, no el cliente.** `generateProjectId`/`generateAppId`/`generateChatId` (slugs tipo `latam-bank-reconciliation`) quedaron sin uso — `createProject`/`createApp`/`registerNewChat` ahora hacen `insert().select().single()` y usan el `uuid` real que devuelve Postgres. Alternativa descartada: mantener los slugs como PK (cambiando las columnas `id` de `uuid` a `text`) para no tener que convertir estas 3 funciones (y sus llamadores directos: `startNewProjectFlow`/`startNewAppFlow`/`startChat`) a `async` — se descartó porque hubiera cascadeado en un `ALTER COLUMN TYPE` sobre todas las FKs de 0002-0004 (apps_projects, chats, map_nodes/edges/versions, chat_messages), más riesgoso que el camino elegido. El camino elegido resultó de bajo riesgo real: casi ningún caller de estas funciones necesita esperar su resultado (son handlers de click terminales), así que la conversión a `async` no cascadeó como se temía inicialmente — se verificó call-by-call antes de tocar código (ver memoria de sesión).
- **2026-08-18 — `organization_id` del usuario, cacheado una vez.** No hay selector de organización en la UI, así que `bootstrapDataFromSupabase()` ahora también resuelve `currentOrganizationId` consultando `organization_members` por el usuario logueado (primera membresía, sin manejar multi-org) y lo cachea en una variable de módulo (`currentOrganizationId`), junto con `currentUserId` — ambas se usan en todo insert nuevo (son `NOT NULL` sin default en el esquema).
- **2026-08-18 — `apps_projects` (N:N) se actualiza por diff, no por reemplazo.** Tanto `createApp` (projects iniciales) como `saveAppEdit` (edición) comparan la lista nueva de proyectos contra la anterior e insertan/borran solo lo que cambió en la tabla puente, en vez de borrar todo y reinsertar — evita huecos de inconsistencia si el insert de los nuevos falla después de haber borrado los viejos.
- **2026-08-18 — Fase 3 investigada antes de tocar código: no existía ningún concepto de "chat actual".** Se mapeó a fondo el flujo de mensajes antes de implementar — confirmado que `continueChat()` no tenía forma de saber a qué chat pertenecía un mensaje de seguimiento, y que clickear cualquier chat existente en la vista Chats o el sidebar era un no-op (sin wiring de click en absoluto). El único lugar que "abría" un chat (`openExistingChat`, desde el popover de historial de un proyecto) no restauraba nada real — fabricaba un intercambio de 2 mensajes falsos, porque literalmente no había historial guardado en ningún lado. Alcance elegido para esta fase: introducir el estado real (`currentChatId`) y hacer que ese único punto existente cargue historial real, sin construir navegación nueva hacia chats desde la vista Chats/sidebar (ver Pendiente) — eso es un gap de UI preexistente, no algo que la persistencia por sí sola debiera resolver.
- **2026-08-18 — `currentChatId`: una sola variable de módulo, fijada/limpiada en los puntos que ya existían.** Se fija al crear un chat (`registerNewChat` dentro de `startChat`) o al reabrir uno (`openExistingChat`); se limpia en los 3 puntos que ya vaciaban `#chatMessages` (`showProjectChatGreeting`, `showAppChatGreeting`, el reset global de "New Chat") — ningún lugar nuevo, solo una línea agregada a cada uno ya existente.
- **2026-08-18 — Bug encontrado y corregido de paso: `sendFromDocked` decidía "¿primer mensaje?" mirando `chatMessages.children.length === 0`.** Con la conversación fabricada de antes, un chat reabierto siempre tenía 2 mensajes falsos, así que ese conteo nunca daba 0. Con historial real, un chat reabierto sin mensajes guardados (los 8 chats sembrados en `0003_chats.sql`, por ejemplo) queda con el hilo vacío legítimamente — y ese mismo chequeo hubiera creado un chat nuevo por error en vez de continuar el reabierto. Cambiado a `if (currentChatId) continueChat(text); else startChat(text)` — la señal correcta es si hay un chat activo, no cuántos `<div>` hay pintados.
- **2026-08-18 — Las respuestas "ai" simuladas (canned, `setTimeout` + texto fijo) también se persisten como `role: 'assistant'`.** No hay backend de IA real todavía — se decidió guardar igual lo que efectivamente aparece en la transcripción (incluida la respuesta mock) en vez de solo lo que escribe el usuario, para que reabrir un chat muestre exactamente lo que se vio la primera vez. Si el día de mañana hay respuestas reales de un modelo, este mismo mecanismo (`persistChatMessage` dentro de `addMessage`) no cambia.
- **2026-08-18 — Bug encontrado y corregido: la vista Chats no listaba del más reciente al menos reciente.** `loadChatsFromSupabase()` (Fase 1) hacía `select('*')` sin ningún `.order()` — sin ordenar explícitamente, Postgres devuelve las filas en el orden que le resulte más conveniente (típicamente el físico de inserción, pero no está garantizado por el motor), no por fecha. Fix: `.order('created_at', { ascending: false })` agregado a esa consulta. No hizo falta ningún sort del lado del cliente — `registerNewChat()` ya hace `CHATS_DATA.unshift(...)` al crear un chat nuevo (el más reciente posible), y ninguna otra operación (pinear/archivar/renombrar) reordena el array, solo muta objetos en su lugar — con el fetch inicial también descendente, todo el array queda consistentemente "más reciente primero". Ver `chats-and-tasks.md`.

- **2026-08-18 — Corrección: los Chats son privados a quien los inició, no compartidos por toda la organización.** Pedido explícito del usuario, con ejemplo concreto: si vos y Juan tienen acceso al mismo Proyecto 1, cada uno ve solo sus propios chats bajo ese proyecto, nunca los del otro — el acceso compartido es al Proyecto (sus datos, su mapa), no a las conversaciones que cada usuario tiene con el agente sobre él. Esto corrige un error real de las policies de `0003_chats.sql`: `select`/`update`/`delete` scopeaban por membresía de organización completa (cualquier miembro veía/editaba todos los chats de la org), no por dueño. `0005_chats_private_per_user.sql` las reemplaza por `owner_user_id = auth.uid()`; `insert` suma ese check al de membresía que ya tenía. Reasigna los 8 chats sembrados en `0003` (quedaron con `owner_user_id` NULL, ningún usuario existía todavía en ese momento) al primer `org_admin` de "Simetrik" para no dejarlos huérfanos. Projects/Apps NO cambian — siguen compartidos por toda la organización, la corrección es específica a Chats/chat_messages. Ver también `proyecto.md` → Reglas clave.
