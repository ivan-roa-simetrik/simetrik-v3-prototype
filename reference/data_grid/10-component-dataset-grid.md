> **Status:** draft (new, 2026-07-31) · **Kind:** surface component · **Lives in:** ⚠️ Inspector · DATA
> Vocabulary per `00-vocabulary.md`. Surfaces per `01-information-architecture.md`.
> Objects it renders: `objects/dataset.md` · `objects/rule.md` · `objects/ruleset.md` · `objects/trigger.md`.
> Runtime it is built against: `09-demo-runtime-spec-PEP.md`.
>
> **Built and interactive:** `components/spreadsheet.html` — open it, it works.
> **Data:** `datasets/` — all 13 PEP Datasets, generated by running the spec's rules.

---

## 1. Purpose

> The spreadsheet a person opens to look at rows, take some away with them, and add a column.

`objects/dataset.md` §8 calls the DATA tab **"the most important surface in the product — every
judgment a finance person makes starts by looking at rows."** This is that surface.

## 2. What it does

Five things, and the fifth is the one that carries product weight.

| | Does | Why it is in v1 |
|---|---|---|
| **Read** | Sticky header, sticky row gutter, per-column type formatting, named Views | The argument in F3 §5c: reading the Rules is not enough, the user must see the output |
| **Copy** | Cell, range, column, row, everything → TSV on the clipboard | Every finance person's real workflow ends in Excel. Refusing to let them take rows out is a fight we lose |
| **Reorder** | Drag a header | A production Dataset has 33 columns and no useful default order |
| **Resize** | Drag the divider, double-click to fit | Column widths are how a person makes 33 columns readable |
| **Add a formula column** | Composed as a **Rule**, placed in a step that carries a **Trigger** | §5 |

### The ground is paper

✅ *Decided 2026-07-31.* **White, in both themes, and it opens Light regardless of the operating
system.** The neutrals are the brandbook's true greys with no hue bias; the dark theme is a neutral
charcoal, not a tinted one.

**Blue is spent only where the product is saying something** — a selection, a rule, a focused
control. It is never the ground.

> **Why this is a rule and not a preference.** The people who live in this screen read Excel and
> Sheets all day, and both are white. A tinted ground makes the one surface that is supposed to feel
> familiar feel like somewhere else — which costs exactly what `value-proposition-v3.md` driver #1 is
> trying to buy. It also makes the provenance rails (§4) harder to read: rails only work as an
> information layer if the ground carries no hue of its own to compete with them.
>
> A first pass used a deep indigo ground because it looked like the brand. It was wrong, and the
> brandbook's own neutral scale — `#FFFFFF` `#F8F8F8` `#F3F3F3` `#DEDEDE` `#C4C4C4` … `#111111` — is
> pure grey precisely because Simetrik is a product people work in, not a deck they look at.

A theme switch sits at the top of the page and the choice persists. It exists so the design can be
reviewed in both, not because the default is in doubt.

## 4. The provenance rail

**The one thing this grid does that a normal spreadsheet does not.** A 2px bar across the top of
every column header, coloured by where the column came from.

| Rail | Origin | Means |
|---|---|---|
| Gray 200 | **as received** | Arrived on the file exactly as it is. No rule touched it |
| Blue 700 | **written by a rule** | A rule computed it. The `ƒ` marker opens the rule and its trigger |
| Blue 400 | **from a side** | Inherited from side A or B of a reconciliation — the `a.` / `b.` prefixes |
| Violet 700, dashed | **proposed** | Composed but not run. Dashed because it is not yet a fact |
| Gray 100 | **system** | Provenance and reconciliation bookkeeping. Deliberately quiet |

> **Why it earns its place.** Driver #3 is *"what finance sees is what runs."* Everywhere else in the
> product that is a claim the user has to take on trust or go and verify in the RULES tab. Here it is
> a property of the table itself: a controller scanning the header row can tell which numbers a
> counterparty sent and which ones we computed, **without clicking anything**. The `ƒ` marker then
> takes them from "we computed this" to the exact rule and the exact trigger in one click.

**The column tags sit in the header too** — the labels themselves, in the order
`12-column-tags.md` §1b fixes, `#fixed` rendered as the padlock and `#match-key`,
`#unique-identifier` and `#sensitive` picked out because a reader scans for them:

```
#date 🔒            #identifier #match-key 🔒     #identifier #sensitive 🔒     #money #zar #match-key 🔒
CREATED_AT          GATEWAY_ID                     SMARTCARD_NUMBER              TXN_VALUE
```

**Verbatim and lower-case.** The meta line is the one place in this component that does **not** uppercase
its text: a label is a token the user types, and `#match-key` is not `#MATCH-KEY`.

That padlock is `objects/dataset.md` §7.2 made visible: *a fixed column is never modified, by anyone or
anything, once set.*

**The denomination label carries the most weight for the least room.** A controller scanning `D08` sees
`#money #zar` on side A and `#money #multi-currency` on side B, on a row where the two are matched against
each other. That is `12-` §6 finding 1 visible at a glance instead of after reading five Rulesets.

> ⚠️ **The `#sensitive` label is declared, and masking is not built.** The label renders; the values under
> it do not change. `12-` §12 has masking as undesigned, and the fixture's `SMARTCARD_NUMBER` values
> happen to arrive part-masked from the source — the generator's doing, not the grid's. `CUSTOMER_NO` sits
> beside it in full, which is exactly the gap.

`#system` and `#reconciliation-metadata` replaced the hardcoded list of column names the first build used
to decide which rail was the quiet one. The grid reads the labels now — same output, and it no longer
drifts when a Dataset gains a bookkeeping column nobody remembered to add to the list.

**The Dataset's own labels sit in the identity bar** — `#daily-merchant-report` `#internal-record`
`#normalized` `#transaction-level`. Different vocabulary, same shape (`11-` §3).

## 5. Adding a column — the part that is a product decision

**A formula column is a `derive` Rule.** That much is `objects/rule.md` §3. The problem is the rest
of the sentence.

### 5a. A Rule has no trigger. A step does.

`objects/ruleset.md` §3 puts triggers on the **Ruleset**, not the Rule, and
`objects/trigger.md` §10.6 makes **zero triggers a validation error, not a configuration**. So
"a formula column with its trigger" cannot be one field on a form. The composer asks it as two:

| Choice | What happens | Default |
|---|---|---|
| **Add to a step that already runs** | The rule joins that Ruleset and **inherits its triggers**, shown in full so nothing is implicit — *"inherits this step's trigger — when D03.V1 changes"* | ✅ yes |
| **Start a new step** | A new Ruleset, which must then pick **at least one** trigger from the closed enum of six | — |

**Appending is the default and it is the right one.** Almost every new column belongs to the step
that already builds the Dataset. Forcing a trigger choice every time teaches people to pick one
without reading it — which is worse than not asking.

Picking "start a new step" with no trigger disables the save and says why: *"A step nothing can
start is dead logic that looks alive."*

### 5b. It produces a proposal, not a fact

The composed column lands **violet and dashed**, its cells washed, with a banner naming the step it
changed and stating that the step has not run. `Discard` removes it.

This is the compromise §7 describes. Nothing is committed from the grid.

### 5c. The guardrails are refusals, not warnings

| Attempt | Response |
|---|---|
| Name collides with a `fixed` column or a key | **Refused.** *"It is a match-key — nobody may modify it, so a rule cannot write it either."* |
| Formula references no column | **Warned.** `objects/rule.md` §3 — a derive rule must use at least one, unless deliberately constant |
| Formula does not parse | **Refused**, naming the character or token that broke it |
| New step, no trigger | **Refused** — §5a |

Per `objects/rule.md` §7.2, these surface as **the product explaining why it can't**, never as a
failed run the user has to decode.

### 5d. Live preview

The composer evaluates the formula against the first rows of the current View and shows the input
columns beside the output. The evaluator implements `09-demo-runtime-spec-PEP.md` §6 — `date()`,
`weekday()`, `text.left/right/find()`, `is_empty()`, `IF … THEN … ELSE`, `x ± N days`, `today`,
and day-name constants — so the spec's own rules run verbatim.

**The same evaluator runs the View conditions.** All 28 Views across the 13 Datasets filter for
real; the counts on the view rail are the ones the rules produce. That is not a demo shortcut, it
is the point: a View *is* a `filter` rule, and a formula column *is* a `derive` rule, so one engine
is the honest implementation of both.

to be a number the recipient can compute with.

## 7. Open questions

**Blocking**

- **Can a column be authored from the grid at all?** F3 §11 reads **no** for v1 — the chat is the
  only way logic changes, because hand-edits create two sources of truth. But a spreadsheet with a
  ＋ on the header row is the most expected affordance this surface has, and a finance person adding
  a column is describing intent, not writing code.
  **What is built is the compromise:** the grid *composes* and the result is a *proposal*. If the
  team lands on chat-only, the ＋ stays and hands the composed rule to the chat instead of applying
  it. **This is the decision the component exists to force.**
- **Are column order and width per person, or per View?** Treating them as personal view state is
  the cheap answer. But an operator who builds a break-investigation layout wants their team to open
  the same one, and a 33-column Dataset has no useful default order. The likely shape is a saved
  arrangement **per View**, owned like the View is — which makes column order part of the control's
  definition, and therefore versioned. Nothing in the model has this.

**Needs deciding**

- **How large is too large to show?** `objects/dataset.md` §10 raises it; this does not answer it.
  It renders every row it is handed. Windowing is a build concern, but **what the status bar says
  when the grid is showing a slice of a much larger truth** is a design one, and it is undesigned.
- **Can a cell be edited directly?** Not built. `01-information-architecture.md` §7 has it open, and
  it is bigger than it looks — a direct edit is a data mutation outside the chat, needing its own
  attribution and approval. The one legitimate route already exists: an `input` rule, which declares
  that a person's judgement goes in that column. The composer offers `input` as a rule type for
  exactly that reason.
- **Row-level visibility.** `objects/dataset.md` §10 — can two people with View see different rows?
  The grid has no concept of it. → F7
- **Where do the a./b. prefixes come from in the UI?** A reconciliation result shows
  `a.gateway_id` and `b.gateway_id` side by side. That is engine vocabulary leaking into the most
  user-facing surface there is, and `00-vocabulary.md` §8 says we do not do that. **No proposal yet.**

**Smaller**

- Sorting is not built. Does sorting a View mean anything, or is order a property of the data?
- Should hiding a column be possible without changing the View that defines it?
- The `ƒ` popover is a third level of detail the IA does not have — `objects/rule.md` §8 asks
  whether a Rule is selectable. This quietly assumes "inspectable but not selectable."

## 8. Test data

`datasets/` — the **PEP Settlement & Bank Confirmation** control from `09-demo-runtime-spec-PEP.md`,
all 13 Datasets, generated by running each Ruleset's rules in its stated arrangement. Every derived
column holds what that rule would actually have written.

| | |
|---|---|
| `datasets/generate.py` | Deterministic generator, seeded. Re-run it and you get the same rows |
| `datasets/csv/` | 13 CSVs, 5,072 rows |
| `datasets/pep-datasets.json` | Full bundle — rows plus `{name, format, tags[]}` per column and a label list per Dataset, Rulesets, triggers, Views. `generate.py` will not emit an amount that names no denomination — a completeness check on the fixture, not product behavior (`12-` §8.2) |
| `datasets/pep-datasets.slim.json` | 120 rows per Dataset, rows stored positionally. What the component embeds |
| `components/build.py` | Inlines the slim bundle into the component |

**It is dirty on purpose.** Every branch of the control has data that reaches it:

- The reconciliation cascade fires on **all three** passes — a resend the processor filed under its
  own reconciliation id is only caught by pass 3 (`gateway + amount`)
- 105 rows unmatched on side A, 70 on side B
- Youth Day, 16 June, pushes a settlement's expected bank date to the 17th through the D02 calendar
  lookups — so `HOLIDAY_NAME` and `FINAL_DATE` are not always empty
- Duplicate rows, reversals, and rows with no gateway id — so `UNIQUE`, `DUPLICATE_21` and the View
  conditions have something to remove
- Bank statement noise with no `PEP MOMENTCO` reference, so `REGEXP_EXTRACT22` has to work
- One day where the bank is short by 318.75 — past the 50 tolerance, so D12 breaks and D13 records it

### Finding — D02 has to be a calendar, not a holiday list

`09-demo-runtime-spec-PEP.md` §8 lands D02 from the same public-holiday file as D01. But RS08b R3
looks up `D02.NWD_2 where D02.DATE_T = NW_DATE` for **any** settlement date, which only resolves if
D02 holds a row per calendar day. Generated as a full calendar, 1 June – 30 September.

**Either the source config has a latent bug, or the runtime spec lost a step in transcription.**
Worth checking against the original `PEP_R02_EXT_vs_BANK.json` before this is built.
